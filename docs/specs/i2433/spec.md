# Ordered HTTP versions for Vert.x SOAP clients

Issue: [#2433](https://github.com/quarkiverse/quarkus-cxf/issues/2433).
Status: draft, based on branch `261118-prepare-for-h3` at `7033f28f` and the issue as read on 2026-11-19.
AI-generated by Codex on behalf of Peter Palaga.

## Background and motivation

SOAP clients need to distinguish a preferred HTTP version from an explicit list of permitted versions
before Quarkus CXF adds HTTP/3 support.
The existing `quarkus.cxf.client."client-name".version` setting supports HTTP/1.0, HTTP/1.1 and HTTP/2,
but selecting `2` retains implicit fallback and cannot require HTTP/2 alone.

Peter Palaga's initial configuration documentation and parser provide a useful starting point for this change.
Its description delegates details to
`CxfClientConfig`, which declares `vertx.http-versions` and documents automatic h2c selection.
This draft follows that declaration; the naming and edge-case decisions below remain proposals for review.

For plaintext HTTP, a bodyless `OPTIONS` upgrade preflight lets Vert.x establish the protocol before sending SOAP data.
Prior knowledge permits a direct HTTP/2 connection to a server known to support it.
Quarkus CXF should translate configuration and validate combinations;
Vert.x should continue to own negotiation, upgrade exchanges and fallback.
This is a medium-sized client transport change with compatibility and protocol-level verification needs.

## Use cases

- **UC1:** Prefer HTTP/2 with HTTP/1.1 fallback using `vertx.http-versions=2,1.1`, over HTTP or HTTPS.
- **UC2:** Require HTTP/2 using `vertx.http-versions=2`, over HTTP or HTTPS.
- **UC3:** Select HTTP/1.0 or HTTP/1.1 explicitly, or supply an ordered list of permitted versions.
- **UC4:** Upgrade existing applications without changing legacy version selection,
  and migrate deliberately to the new list with documented behavior changes.

## Use case validation

- **UC1 and UC2 are partly implemented:**
  [CxfClientConfig.VertxConfig](../../../extensions/core/runtime/src/main/java/io/quarkiverse/cxf/CxfClientConfig.java)
  already declares and documents `httpVersions()`.
  [CXFClientInfo](../../../extensions/core/runtime/src/main/java/io/quarkiverse/cxf/CXFClientInfo.java)
  parses an immutable ordered list, checks duplicates and rejects a simultaneous non-`auto` legacy version.
  Its error messages need to replace `vertx.versions` with `vertx.http-versions`.
  The parsed list has no transport consumer yet:
  [HttpClientPool](../../../extensions/core/runtime/src/main/java/io/quarkiverse/cxf/vertx/http/client/HttpClientPool.java)
  still creates clients using a single `HttpClientOptions.protocolVersion`.
- **UC1 already has a partial workaround:** legacy `version=2` prefers HTTP/2 with fallback,
  but does not provide the new preflight guarantee or exact list semantics.
  An extension can customize `HttpClientOptions` through `HttpClientCustomizerBuildItem`,
  but this is not an equivalent application configuration interface.
- **UC2 needs explicit transport wiring:** Quarkus 4.0.0.CR1 manages Vert.x 5.2.3.
  Its `HttpClientConfig(HttpClientOptions)` normally expands legacy `HTTP_2` into `[HTTP_2, HTTP_1_1, HTTP_1_0]`.
  The new list must bypass that implicit expansion.
  Vert.x exposes an ordered list through
  [HttpClientConfig.setVersions](https://vertx.io/docs/apidocs/io/vertx/core/http/HttpClientConfig.html#setVersions(java.util.List)).
- **UC3 has transport limits:** Vert.x 5.2.3 selects the first list entry for plaintext connections.
  If it is HTTP/2 with upgrade enabled, upgrade and fallback use HTTP/1.1.
  Therefore plaintext `2,1.0` cannot safely use that upgrade path.
  Appending `1.0` to `2,1.1` does not add a retry using HTTP/1.0.
  A valid HTTP/1.0 response to an HTTP/1.1 request does not change subsequent outgoing requests to HTTP/1.0.
  HTTPS uses ALPN when HTTP/2 is included; without negotiated ALPN, Vert.x selects the first permitted HTTP/1.x version
  or fails when there is none.
- **UC4 has existing regression coverage:**
  [ClientHttp2Test](../../../extensions/core/deployment/src/test/java/io/quarkiverse/cxf/vertx/http/client/ClientHttp2Test.java)
  exercises legacy `version=2` against an HTTPS HTTP/2 server.
  `KeepAliveTimeoutTest` covers connection behavior for multiple versions.
  New coverage must distinguish actual requests and negotiated protocols, not just configuration values.

The transport observations above come from the locally available `io.vertx:vertx-core:5.2.3:sources` artifact,
particularly `HttpClientConfig`, `HttpClientBuilderInternal` and `TcpHttpClientTransport`.
Vert.x's [Http2ClientConfig API](https://vertx.io/docs/apidocs/io/vertx/core/http/Http2ClientConfig.html)
provides both the prior-knowledge switch and bodyless preflight support.

## Scope

Goals:

- Complete the ordered-version configuration for `VertxHttpClientHTTPConduit`. esp. in `HttpClientPool`.
- Derive h2c establishment from the list and enforce the permitted versions.
- Preserve legacy selection when the new setting is absent.
- Provide actionable validation, migration documentation and focused protocol tests.

Non-goals:

- HTTP/3, QUIC, Alt-Svc discovery or SOAP server configuration.
- A Quarkus CXF negotiation engine, version-by-version retry loop or new SOAP replay mechanism.
- New capabilities for `URLConnectionHTTPConduit`.
- A general redesign of connection pools, TLS, proxies, authentication or keep-alive settings.

## Functional requirements

In this section, `http-versions` abbreviates `quarkus.cxf.client."client-name".vertx.http-versions`.

### FR1: Configuration contract and validation

Accept an ordered list containing distinct values from `1.0`, `1.1` and `2`.
Preserve the order and pass the list to Vert.x without adding fallback versions.
Reject unsupported tokens, including `3` and `auto`, duplicate entries and a present empty list.
An absent setting uses legacy behavior; an empty property that configuration binding treats as absent does likewise.
Diagnostics must identify the client, the canonical property name and the invalid value or combination.

Reject `http-versions` together with a legacy `version` other than `auto`.
When the list is active, reject CXF per-request version overrides before dispatching the request,
including `FORCE_HTTP_VERSION` and `org.apache.cxf.transports.http2.enabled`.
Neither overrides nor a programmatically changed HTTP client policy may silently replace the explicit list.
Reject an explicit list when the effective conduit is `URLConnectionHTTPConduit`, rather than silently ignoring it.
Validate static conflicts during client initialization and request-specific conflicts before sending SOAP data.

### FR2: Plaintext HTTP behavior

| Ordered list | Required behavior |
| --- | --- |
| `2` | Direct HTTP/2 prior knowledge; no HTTP/1.x upgrade or fallback. |
| `2,1.1` or `2,1.1,1.0` | Bodyless HTTP/1.1 `OPTIONS` preflight; use HTTP/2 on upgrade or HTTP/1.1 on refusal. |
| `2,1.0,1.1` | Same upgrade behavior; retain the list order, but document that h2c fallback uses HTTP/1.1. |
| A list starting with `1.0` or `1.1` | Use that first version; do not attempt h2c or cycle through later entries. |
| `2,1.0` | Reject for plaintext HTTP because h2c upgrade would use unlisted HTTP/1.1. |

Enable Vert.x preflight when the first version is `2` and `1.1` is also permitted.
A successful upgrade continues on the upgraded connection.
A normal refusal permits Vert.x to proceed using HTTP/1.1 where the connection remains usable.
Network errors and failed negotiation remain failures; Quarkus CXF must not invent additional retries.
The preflight must not contain the SOAP body, and its response must not be delivered as the SOAP response.
Reused connections must not perform a new preflight for each SOAP invocation.

### FR3: HTTPS behavior

When HTTP/2 is listed, advertise the permitted protocols in configured order through ALPN.
The server selects the negotiated protocol; client order expresses preference and cannot force server preference.
Do not perform an h2c preflight over HTTPS.

`2,1.1` must work with an HTTP/2 server and with a server that only supports HTTP/1.1,
including a server that does not negotiate ALPN.
`2` must fail if HTTP/2 is not negotiated, before any HTTP/1.x SOAP request is sent.
Without ALPN negotiation, use only the first permitted HTTP/1.x version, if any.
Lists containing only HTTP/1.x use their first entry; do not promise ALPN ordering for that case.
HTTPS `2,1.0` is permitted because its fallback does not require an HTTP/1.1 upgrade.

### FR4: Legacy compatibility and client lifecycle

With `http-versions` absent, preserve the legacy `version` default of HTTP/1.1,
explicit `1.0` and `1.1`, and the HTTP/2 preference and fallback associated with `version=2`.
Preserve the legacy override mechanisms in that mode.
Apply the new preflight behavior to legacy clients too and make sure it is properly documented.

An explicit list must remain effective across pooled requests, client recreation and TLS certificate updates.
Keep named clients with different lists independent.
Evaluate scheme-dependent behavior against the effective destination, including endpoint overrides and redirects
where those features are already supported.
Preserve unrelated options supplied by existing customizers;
customizers and TLS configuration must not silently broaden the explicit permitted-version list.

### FR5: Documentation and proposed decisions

Update configuration Javadoc if needed, the generated reference and migration guidance with the HTTP/HTTPS behavior matrix,
validation errors and examples for each use case.
Quarkus CXF 4.0.0 enables bodyless preflight for plaintext HTTP/2 upgrade connections, including legacy version=2.
Explicit http-versions=2 uses prior knowledge without preflight.
Explain that `http-versions=2` removes the fallback while `http-versions=2,1.1` permits fallback and includes preflight on plaintext connections.

Resolve the issue's ambiguities as follows:

- **Name:** use `vertx.http-versions`, matching the existing config declaration and reference.
  Do not introduce `vertx.versions` as an alias for an unreleased draft name.
- **h2c control:** infer the strategy from the list and introduce no separate `vertx.h2c` setting.
  Treat the issue's reference to a configured h2c mode as superseded by its explicit automatic-selection description.
  Remove or reconcile the unused `H2cMode` enum.
- **Warning:** do not retain the issue's requested client-creation warning for plaintext `2`.
- **Unsupported plaintext combinations:** document that `http-versions` having `2` at the first position and containing `1.1` on some later position
  is the only fallback for 2 (namely to 1.1). A fallback to 1.0 does not work on clear text. 
  We should refer to Vert.x documentation for details rather than overfitting to the behavior of the current Vert.x version.
- **Other conduits:** fail clearly for an explicit list on `URLConnectionHTTPConduit`;
  leave existing configurations without the list unaffected.

## Non-functional requirements

- **NFR1 — Performance and request integrity:** add no blocking negotiation on event-loop threads,
  additional SOAP-body buffering or SOAP replay solely to select a protocol.
  Keep preflight at connection establishment and retain pooling and streaming behavior.
- **NFR2 — Compatibility:** support JVM and native execution without new transport dependencies.
  Preserve TLS trust and hostname verification, proxies, authentication, timeouts and unrelated customizer behavior.
  Keep existing keep-alive semantics unless a protocol requirement makes a documented adjustment necessary.
- **NFR3 — Security:** an explicit list must not silently permit an excluded outgoing protocol.
  TLS certificate errors must remain errors and must never cause a fallback to plaintext.
  Diagnostics must not expose credentials or SOAP payloads.
- **NFR4 — Maintainability:** keep parsed configuration immutable and delegate transport exchanges to Vert.x.
  Use real local HTTP/HTTPS peers for protocol tests and existing Quarkus/JUnit test styles without mocks.

## Acceptance criteria

- **AC1 (FR1):** configuration tests verify ordered parsing, supported single values, duplicates,
  unsupported values, empty/absent semantics and conflicting legacy settings.
  Failures name the correct client and `vertx.http-versions`.
- **AC2 (FR1, FR4):** each supported CXF version override fails before dispatch when a list is active;
  equivalent legacy configurations remain usable without the list.
  A conflicting programmatic policy and a list on `URLConnectionHTTPConduit` fail clearly.
- **AC3 (FR2, NFR1):** a real plaintext h2c peer observes a bodyless `OPTIONS` upgrade for `2,1.1`,
  then exactly one SOAP invocation over HTTP/2.
  Repeat on a reused connection and verify that there is no additional preflight.
  Include a SOAP body larger than the legacy Vert.x upgrade aggregation limit of 65,536 bytes.
- **AC4 (FR2, NFR1):** a peer refusing upgrade observes a subsequent HTTP/1.1 SOAP request,
  whose response reaches the caller instead of the preflight response.
  Appending `1.0` does not introduce an HTTP/1.0 retry or duplicate SOAP invocation.
- **AC5 (FR2, NFR3):** plaintext `2` sends the HTTP/2 connection preface directly and succeeds with a compatible peer.
  It fails against an HTTP/1.x-only peer without sending an HTTP/1.x SOAP request.
- **AC6 (FR2, FR3):** verify the behavior matrix with real peers, including reversed preferences,
  HTTP/1.x-first lists, rejected plaintext `2,1.0` and supported HTTPS `2,1.0`.
  Check outgoing request versions; an HTTP/1.0 response alone is not evidence of HTTP/1.0 fallback.
- **AC7 (FR3, NFR3):** HTTPS `2,1.1` succeeds through ALPN as HTTP/2 or HTTP/1.1,
  and uses HTTP/1.1 with a peer that negotiates no ALPN.
  Inspect the advertised order, including `1.1,2`, without assuming the server follows client preference.
  HTTPS `2` fails against an HTTP/1.1-only or non-ALPN peer before sending an HTTP/1.x SOAP request.
- **AC8 (FR4, NFR2):** legacy default, `1.0`, `1.1` and `2` behavior remains covered,
  including existing HTTP/2 and keep-alive regressions.
  Different named clients, pooled reuse, TLS updates and supported destination changes retain the intended lists.
  Verify representative TLS, proxy, authentication and customizer configurations after transport wiring changes.
- **AC9 (NFR1–NFR4):** focused JVM and native tests demonstrate the new selection behavior,
  streaming a large SOAP request and preserving TLS verification failures.
  Review confirms immutable parsed lists and no Quarkus CXF implementation of negotiation or protocol retries.
- **AC10 (FR5):** configuration reference and migration examples consistently use `vertx.http-versions`
  and explain automatic h2c selection, HTTPS ordering, fallback limits and the legacy/new `2` distinction.
- **AC11 (FR2, FR3, FR4, NFR1, NFR2):** with `http-versions` absent and legacy `version=2`,
  a real plaintext peer observes a bodyless `OPTIONS` preflight before the SOAP request.
  Verify both successful upgrade to HTTP/2 and upgrade refusal followed by HTTP/1.1 fallback,
  using a SOAP body larger than 65,536 bytes in each case.
  Each invocation reaches the SOAP service exactly once
  and returns its SOAP response rather than the preflight response.
  Repeating an invocation on the same pooled connection sends no additional preflight.
  Repeat these scenarios with HTTP/2 selected through each legacy override:
  `FORCE_HTTP_VERSION=2` and `org.apache.cxf.transports.http2.enabled=true`.
  Legacy default, `version=1.0` and `version=1.1` clients without HTTP/2 overrides send no h2c preflight,
  and HTTPS clients continue to use TLS protocol selection without h2c preflight.
